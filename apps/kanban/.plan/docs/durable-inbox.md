# Durable desk inbox storage

`src/state/durable-inbox-store.ts` stores desknote and handoff notifications in an existing registered Kanban workspace under an explicit physical `KANBAN_STORAGE_ROOT`. The tenant and workspace each have a hashed directory component. The stored file includes the original tenant and workspace IDs and rejects a scope mismatch. Publication is serialized with a file lock and written atomically before a caller sends any WebSocket notification.

Each event has a stable ID, destination desk, sender attribution, an explicit snapshot of one to 32 recipient session IDs, time, and a bounded desknote reference and digest. Optional text is capped at 4,000 characters and its SHA-256 is checked against its exact UTF-8 bytes. A reference and digest without text are declared by the publisher; this store does not fetch or authenticate the referenced note. Raw transcripts are outside this event format.

An identical repeated event ID returns `replay: true`; the same ID with a changed payload is refused. Pending reads are scoped to one exact tenant, workspace, and recipient session, sorted by event time and ID, and return at most 100 events with `hasMore`. A recipient can acknowledge only an event whose recipient snapshot includes it. Acknowledgement records consumer receipt, not model reading, session liveness, desk authorization, or task completion. A repeated acknowledgement returns `{ acknowledged: true, replay: true }` because the recipient remains acknowledged; other recipients remain pending. An unknown event returns `{ acknowledged: false, replay: false }`. Unacknowledged events remain available after runtime restart.

The version 1 namespace file has a 4 MiB and 512 event limit, including acknowledged events. It refuses additional publications at capacity rather than allowing unbounded reads or rewrites. Operational rotation or archival would need a separate migration that preserves event ID deduplication and pending receipts.

## Runtime transport

The local runtime exposes typed tRPC procedures `inbox.publish` (full event envelope), `inbox.pending` (`{ tenantId, workspaceId, recipientSessionId, limit? }`), and `inbox.ack` (`{ tenantId, workspaceId, eventId, recipientSessionId }`). Requests carry the same `x-kanban-workspace-id` header or `workspaceId` query parameter as other workspace procedures; the envelope workspace ID must match that resolved workspace. A successful first publication is saved before the server attempts live notification. A duplicate publication returns `replay: true` and does not generate another live notification.

Clients use the existing `/api/runtime/ws?workspaceId=<id>` socket and explicitly send `{"type":"inbox_subscribe","tenantId":"...","workspaceId":"...","recipientSessionId":"...","limit":100}`. The server accepts only the socket's resolved workspace ID, clears the previous subscription on switch, and sends each pending envelope as `{"type":"inbox_event","event":...}`. After the pending page, it sends `{"type":"inbox_subscribed","tenantId":"...","workspaceId":"...","recipientSessionId":"...","replayed_count":0,"has_more":false}` with actual counts and `has_more`. There is no cursor in version 1; a consumer can acknowledge received events and request pending again to advance. Live fanout sends only to sockets subscribed to the event's exact tenant, workspace and recipient session ID. A malformed subscription clears the old selector.

Delivery is at least once: a live event can overlap replay, and consumers should deduplicate by the stable `event_id` within its tenant and workspace. The selector identifies a requested recipient; it is not proof of that recipient's identity or that an agent read the envelope. This first slice uses the runtime's existing trusted local access boundary and does not dispatch an LLM or terminal action.
