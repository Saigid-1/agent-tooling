# ADR planning in native Kanban

Open **ADR planning** above the native board. Initiatives group ADR IDs across the registered repository workspaces; each execution track retains its explicit workspace and card link. A workspace is a Git repository, not an initiative.

Before slices exist, **Add an ADR before creating slices** retains a snapshot of a repository-relative Markdown file. Registration records exact working-tree content SHA256 and repository HEAD separately. It does not claim those bytes were committed. Re-registering identical content is idempotent; changed content remains alongside earlier snapshots. The physical index is bounded to 100 snapshots and 8 MiB and validates retained content hashes.

Select an ADR to inspect its snapshots, declared and intake-derived status, unresolved questions, full reviewed intake, and native execution tracks. **Add a reviewed execution slice** accepts a physical approved intake JSON path, an explicitly selected execution repository, and its pinned 40-character commit. An optional prior intake SHA256 authorizes a revision. This uses the same native reconciliation as the CLI and never starts execution. **Open native card** enters the existing card, worktree, chat and Start controls; **Native Kanban** returns to the existing board.

**Start / resume architectural chat** uses native Cline workspace chat in plan mode and loads retained conversation history. No planning session starts from opening the page. Resuming retains previously sent context; **Send refreshed planning context** explicitly appends the currently prepared snapshots in plan mode without replacing conversation history. The initial provider context contains current document snapshots and reviewed intakes, bounded to 24,000 characters, with visible notices for historical exclusions, excerpts and omissions. Complete sources remain available in the view. The chat runs in the currently selected repository and does not grant a desk admission.

Requirement evidence uses canonical intake scenario IDs (`acceptance:1`, `acceptance:2`, etc.). Each record requires a physical evidence file and SHA256, rationale, current intake, and an idempotent request ID. UI records are labeled local operator assertions, not authenticated human approvals. Acceptance and amendment proposals follow the backend evidence rules; a proposal does not edit source ADR Markdown. Native lifecycle observations and capture gaps remain separate from requirement proof.

The active repository's board and sessions use the existing real-time stream. Other registered repositories and evidence records refresh every five seconds, with explicit error messages when reads fail. No board is cloned and no dispatcher is introduced. The runtime must use its configured physical storage root. This view registers existing ADR files and reviewed intake packages; it does not synthesize an approved intake or acceptance from a conversation or board movement.
